# CPU baseline: 12 November 2026

We obtained these measurements with the installed Windows wheel on an Intel
Core i7-13700KF (24 logical CPUs), running Windows 11, Python 3.14.3, NumPy
2.5.4, and PyTorch 2.15.0+cpu. The C++ extension was built in Release mode
with MSVC 19.50. Each number below is the median of five fits after one warmup,
using random seed 20261112.

No thread settings were overridden through environment variables. PyTorch
reported 16 CPU threads; that describes its configuration, not how many threads
Bagel uses.

We describe how to repeat the run in the [benchmark guide](README.md). The
[JSON file](baseline-2026-11-12.json) contains all the timings, environment
details, and file hashes. The local installation path has been replaced with
a placeholder so the report can be shared.

The default is known variance and approximate merging distance; the last two
rows change one of those settings. Joint change models have twice the listed
coefficient dimension. All use `bagel` pruning and process the full input.

## What the timings tell us

NumPy and CPU tensor inputs took almost the same time: every median difference
was below 1%. Both used NumPy model functions. The small differences in either
direction are too small to treat as a speed advantage.

Converting one CPU tensor series took roughly 0.10 ms in the separate conversion
measurement, compared with about 140 ms for the mean-change fit. That suggests
conversion is a minor part of the cost here, although timings this short are
sensitive to Python overhead, timers, and cache effects.

Model size and particle count had a much larger effect. Raising the particle
limit from 32 to 128 made the mean-change fit about 3.7 times slower. Raising
the number of baseline coefficients from 1 to 16 made it about 6.2 times slower.

The instrumented mean-change run called the model functions 98,416 times.
Their bodies took about 17% of update time, falling to about 3% in the
16-coefficient case. The rest includes C++ work, validation, tensor checks,
Python calls, and instrumentation.

A separate cProfile run attributed 0.128 s of 0.217 s of internal function
time to the native update call, excluding its Python callbacks. Feature
construction took 0.026 s, and the Python prior adapter took 0.017 s. Profiling
adds overhead, so these figures help locate costs but should not replace the
fit timings in the table. The native call also includes pybind conversion
and validation; it is not a measurement of the algorithm alone.

For small models, we can investigate callback frequency and adapter overhead
next. For larger models, we can profile the C++ code to locate the cost.
These CPU measurements do not tell us whether a GPU implementation would
be faster; Bagel has no GPU compute backend at present.

## Checks and scope

At the time of this benchmark, the installed wheel passed 117 tests, including the R-reference
comparisons, tensor/NumPy agreement, streaming input, tensor callbacks,
input validation, and NumPy use with PyTorch imports blocked. One CUDA transfer
test was skipped because the test environment uses CPU-only PyTorch. The
benchmark also checked output agreement before timing every workload/input.

These results cover synthetic data on one machine. Tensor observations were
detached and converted to CPU float64 before fitting. The runs did not measure
tensor callbacks, GPU transfers, automatic differentiation, or parallel series
processing. The R interface and shared C++ algorithm were unchanged for this
benchmark.
